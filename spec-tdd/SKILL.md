# Spec + TDD 功能实现

使用规格驱动 + 测试驱动的流程实现一个功能：先生成完整的规格文档，再按 TDD 模式逐模块实现。

## 输入

`$ARGUMENTS` — 用户对该功能的需求描述。

若未提供参数，向用户询问：
1. 这是哪个阶段（编号）
2. 这个阶段要做什么

## 阶段一：生成规格文档

### 第一步：理解需求

1. 解析用户的需求描述
2. 读取 `docs/PLAN.md`，结合已有规划理解上下文
3. 如有不清楚的地方，先向用户确认再动手

### 第二步：创建目录和文件

```
docs/phase{N}/
├── 1-proposal.md
├── 2-design.md
├── 3-test.md
├── 4-task.md
└── test/
    └── test-{模块名}.md  （每个模块一个文件）
```

### 第三步：编写 1-proposal.md

**只写业务规则，不写实现和模块设计。**

内容包括：
- 目标（一句话描述要实现什么）
- 业务规则（用户可感知的行为，如页面流程、交互规则、数据规则）
- 约束条件（如有）

不要包含：
- 技术方案、模块划分、函数签名
- 代码片段
- 依赖关系

### 第四步：编写 2-design.md

**只写设计思路，不贴代码。**

内容包括：
- 总体架构（模块划分、依赖关系图）
- 每个模块的职责和设计思路
- 关键设计决策及其理由
- 模块间的数据流

不要包含：
- 代码块、函数实现
- 具体的类型定义代码

### 第五步：编写 test/ 下的测试规格

为每个模块创建一个 `test-{模块名}.md`，使用 **When/Then 中文格式**：

```
- 当 [前置条件/操作] 时，应 [预期结果]
```

按功能分组，每组一个二级标题。覆盖：
- 正常流程
- 边界情况
- 异常/错误情况

### 第六步：编写 3-test.md

**只做索引，不写具体用例。**

内容包括：
- 测试规格文件列表（表格，含链接和对应源码路径）
- 验收标准（通过/未通过的 checklist）

### 第七步：编写 4-task.md

**将该阶段拆解为可执行的开发任务，采用 TDD 模式：先写测试，再写实现。**

原则：每个模块的任务拆为「先写测试」和「再写实现」两步，遵循 RED → GREEN → typecheck 节奏。

每个模块的任务结构：
1. **先写测试**：按 test/ 下的规格文件创建 `.test.ts`，运行测试确认全部失败（RED）
2. **再写实现**：编写源码让测试逐步通过（GREEN）。复杂模块可按函数进一步拆分实现步骤
3. **收尾**：运行 typecheck 确认零错误

使用 `- [ ]` 格式，方便后续勾选跟踪。任务完成后标记为 `- [x]`。

格式示例：
```
## 任务 N：模块名（TDD）

### N.1 先写测试

- [ ] 按 test-xxx.md 规格，创建 xxx.test.ts
- [ ] 运行测试 → 确认全部失败（RED）

### N.2 再写实现

- [ ] 创建 xxx.ts，实现功能
- [ ] 运行测试 → 全部 GREEN

### N.3 收尾

- [ ] 运行 typecheck → 零错误
```

### 第八步：更新 README

在 README.md 的「开发计划」部分追加新阶段的文档链接。

## 阶段二：TDD 实现

文档生成完成后，按 4-task.md 中的任务列表逐个执行：

1. **按任务顺序逐个实现**，每个模块严格遵循 RED → GREEN → typecheck
2. **先写测试**：根据 test/ 下的规格文件生成 `.test.ts`，运行确认全部失败
3. **再写实现**：编写源码，运行测试直到全部通过
4. **标记完成**：每完成一个任务，在 4-task.md 中将 `- [ ]` 改为 `- [x]`
5. **最终验证**：所有任务完成后，运行全量测试 + typecheck 确认零错误

## 文档风格要求

- 全部使用中文
- 简洁，不啰嗦
- proposal 关注「做什么」，design 关注「怎么做」，test 关注「怎么验」，task 关注「怎么干」
- 四者互不重复
